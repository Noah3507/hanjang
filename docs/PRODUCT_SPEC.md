# Hanjang 제품 요구사항 초안

근거: P3·10·11·14·19, R3·10·13. P/R 표기는 [요구사항 검토](REQUIREMENTS_REVIEW.md)를 따릅니다. **자료 요구**와 **설계 제안**을 구분합니다. 입력·업로드 구현 범위와 후속 광고 기능을 아래에서 구분합니다.

사용자 확정: 자료 충돌 시 최종 발표본 우선. 핵심 우선순위는 **상품 이미지 업로드 → AI 광고 4종 생성 → 선호도 순위 표시 → 문구 수정 → PNG 다운로드**입니다. A4 PDF는 PNG MVP 이후 OPTIONAL이며 최종 필수 완료 조건에서 제외합니다.

## 목표와 범위

현재 구현은 health·상품 입력·원본 업로드·draft와 [사진 전처리/비교/선택](IMAGE_PROCESSING.md)입니다. JPG/PNG 10 MiB·24MP·최소 256px, 이름 80자·가격 40자 검증값을 유지합니다. 원본·처리본·마스크는 비공개이며 같은 24시간 TTL로 정리합니다. 실패/품질 경고 시 원본을 기본 선택하고 성공 시에도 원본 선택이 가능합니다. 광고 생성·ranking·편집·결과 다운로드는 미구현입니다.

사용자는 가게명·상품명·가격·분위기와 사진을 입력해 '상품 정보와 사진 저장'을 누릅니다. 서버 저장 후 GET으로 읽은 값과 pending 상태를 표시합니다. '저장 정보 다시 조회'로 저장값·원본을 다시 읽고 같은 탭의 새로고침 후에도 조회할 수 있습니다. 광고 생성을 시작하지 않습니다. 사용자 입력 사실은 trim/숫자 변환 없이 보존합니다. 필수 누락/길이/제어 문자/잘못된 이미지 오류는 입력을 유지한 채 안내합니다.

소규모 음식점·카페·식품 매장 운영자가 사진 하나로 광고 4개를 비교하고 문구를 수정해 저장할 수 있게 합니다. 모델은 상대 preference를 정렬하며 구매율·매출·CTR을 예측하지 않습니다. 상품 재생성, 자동 SNS 게시, 로그인·결제, 매출 분석은 확인된 범위에 없습니다.

## 사용자 흐름

1. 브라우저 매장 프로필을 불러오거나 가게명·상품명·가격을 입력합니다.
2. 실제 사진 JPG/PNG 한 장을 올리고 분위기를 선택합니다. 분위기는 네 전략 모두에 적용되는 스타일 조건입니다.
3. 생성 중 사진 처리→분석→문구 생성→렌더링→순위·진단 상태를 표시합니다.
4. 전략별 하나씩 총 네 후보를 순위별로 비교합니다. mock이면 데모 순위 표시를 유지합니다.
5. 후보의 생성 문구만 수정합니다. factual field 변경은 입력 화면에서 새 생성으로 처리하는 제안입니다.
6. 수정본 재렌더링 후 네 후보를 다시 ranking합니다. 완료된 최신 revision PNG를 저장합니다.
7. 전체 저장은 D16 제안입니다. A4 PDF는 PNG MVP 이후 선택 확장이며 최종 필수 완료 조건이 아닙니다.

## 입력과 출력

| 입력 | 요구·정책 |
| --- | --- |
| 사진 | 자료: 실제 한 장. 제안: JPG/PNG·D09 제한, EXIF orientation 적용, 원본 파일 보존 |
| 가게명·상품명 | 자료: 사용자 값. 제안: 공백만 있으면 거부, 수락 문자열은 trim·교정·번역 없이 보존 |
| 가격 | 자료: 사용자 값. 제안: `price_text` 예 `10,500원`, 숫자로 변환하거나 단위 추가하지 않음 |
| 분위기 | 자료: 선택. 제안: warm/minimal/vivid/premium, 기본값 없이 선택 |
| 주소·Instagram | P10 프로필 항목. optional, 없으면 영역 숨김, 입력만 사용 |

출력: 전략별 PNG·생성 문구·동일한 사실 입력·rank 1–4·scalar score·model/source version·별도 가독성 진단. [API 계약](API_CONTRACT.md)을 따릅니다. A4는 필수 출력에서 제외하며 PNG MVP 완성 후 별도 선택 작업으로 다룹니다.

| F03 | 사진 처리 | 원본 파일·해시 보존, 배경 제거·비율 유지 resize만 허용. 상품 재생성·형태 변경·색상/채도/명도 보정 금지. 처리 실패·상품 손상 의심·품질 저하 시 원본 fallback 및 사용자가 원본 선택 가능 |

## 전략과 예외

emotional은 분위기·문구, price는 입력 가격, visual은 실제 사진, brand는 입력 가게명을 주요 요소로 삼습니다. 할인·상품 재생성 금지. 사실은 같고 geometry·생성 문구만 다릅니다. [디자인 설계](DESIGN_SPEC.md) 참조.

| 상황 | 동작 제안 | 사용자 안내 |
| --- | --- | --- |
| 입력·크기·형식 오류 | 422/413/415, 생성 시작 안 함 | field와 수정 방법, 입력 유지 |
| decode 오류·압축 폭탄 | 422/413, 임시 파일 정리 | 유효하거나 작은 JPG/PNG 요청 |
| rembg 실패·빈 mask·품질 저하·상품 일부 손상 의심 | 원본 프레임 fallback+warning, 원본 사용 선택 제공 | 배경 제거 미적용, 원본 보존. 자동 mask 검사가 모든 손상을 판별한다고 보장하지 않음 |
| 분석 실패 | 중립 context+warning | 분석 미사용, 사실 단정 금지 |
| LLM timeout·schema·사실 침범 | 최초+1회 재시도 후 failed | 재시도 안내, 임의 문구로 성공 처리 금지 |
| renderer·font·overflow 오류 | job 실패, 4개 미만을 완료로 표시 안 함 | 단계 오류, 입력 유지 |
| 모델 없음·잘못된 응답·timeout | 전체 mock fallback | 실제 모델 미사용 배너 |
| 진단 불가 | unavailable/null, 순위는 유지 | 측정 못함, 양호로 가정 금지 |
| 편집 revision 충돌 | 409, 기존 완성본 보존 | 최신본 읽고 다시 수정 |
| 만료·세션 불일치 | 410 또는 존재 노출 없는 404 | 재생성, 타 사용자 파일 노출 금지 |
| localStorage·다운로드 차단 | 핵심 흐름 유지 | 프로필 저장 불가/개별 저장 안내 |

완료 시간·진행률 숫자를 측정 없이 만들어 표시하지 않습니다. 요청 한도·LLM 공급자는 미확정이며 작업 취소는 MVP 범위에 포함하지 않습니다.

## 확정된 초기 운영 요구사항

- 단일 서버의 비공개 임시 저장과 Job Polling을 사용합니다. 상태는 `pending`(접수), `processing`(처리 중), `completed`(완료), `failed`(실패) 네 가지입니다.
- 작업별 고유 ID로 원본·중간 처리 파일·생성 광고를 연결합니다. 파일 시스템 경로는 응답·오류에 노출하지 않습니다. 고유 ID 자체는 접근 권한을 대신하지 않습니다.
- 업로드·결과 조회·다운로드에서 작업 소유권을 검사하며 외부의 임의 접근을 차단합니다. 공개 정적 폴더·디렉터리 목록을 제공하지 않습니다.
- 각 job 생성 시각을 기준으로 24시간 후 해당 원본·중간 파일·결과물을 모두 자동 삭제합니다. 편집·조회·다운로드로 만료를 연장하지 않는 정책은 구현 세부 제안입니다. 완료·실패 작업 모두 정리 대상입니다.
- 파일 크기·실제 형식/decode·안전한 서버 파일명·저장 경로를 검증합니다. 사용자 파일명이나 입력 경로를 그대로 사용하지 않습니다. 수치 제한은 D09에서 별도로 확정합니다.
- 서버 재시작·배포 시 작업 상태와 파일이 유실될 수 있습니다. 원본 보존은 보관 기간 내 원본을 덮어쓰지 않는다는 뜻이며 영구 보관을 보장하지 않습니다. 유실/만료 시 재업로드를 안내합니다.
- 별도 클라우드 스토리지·복잡한 작업 큐는 MVP에 도입하지 않습니다. 추후 교체 가능한 저장·작업 실행 인터페이스를 분리합니다.
